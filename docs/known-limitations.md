# 已知限制

> 2026-10-30 更新：用户要求已调整为仅保留编辑模式。工作区、连续页面及文字草稿保存的最新实现和仍存在的参考差异，见 [编辑工作区复刻记录](reference-editing-2026-10-30.md)。下文保留早期实现记录，涉及旧工作区布局的描述以本次更新为准。

本文件记录 PDFX 初始版本与规格、M0 原型及原定验收范围之间仍然存在的差异，以及在本环境中未执行的人工验证。这里列出的项目都是有意保留的边界，不是待办清单；修复它们需要单独的设计与实现，不能靠文档更新解决。

## 工作区信息架构

- 生产工作区复刻了参考编辑器的顶部结构：仅编辑模式及其五个页签（注释、形状、插入、编辑文本、表单）、居中的第二行图标工具条、右侧工具属性面板与右下角“保存更改”。同一时刻只有一个工具处于激活状态，切换页签或再次点击会收起工具。工具集合按 PDFX 已实现的能力映射；参考产品中依赖其在线服务的项目（在线印章库、OCR、云端字体等）不在复刻范围内。图章、水印、导出、页面、附件与图层这些 PDFX 专有面板收在“更多工具”菜单中。
- `src/prototype/` 与 `prototype.html` 仍然是信息架构与文案的参考实现，不随生产工作区更新。

## 渲染与性能

- 查看器采用连续页面，当前页使用完整/分块渲染，邻近页面和缩略图按需加载。普通文本移动采用缓存背景与字形；有注释、图层覆盖或无法安全合成的页面保留完整预览路径。
- 打印准备严格按页串行，解码后的 RGBA 位图峰值固定为一页；但每页压缩后的 PNG Blob 会一直存活到打印结束、取消、切换文档或组件卸载。所选范围很大时，压缩 Blob 总量仍可能占用可观内存。真实桌面 WebView 的内存曲线未人工 profile。

## 界面与语言

- 设置中的英文选项只更新 `<html lang>`（以及主题/语言的应用状态），可见文案始终为简体中文；没有 i18n 资源文件。
- 应用级退出（`Cmd+Q` 或菜单“退出 PDFX”）不经过窗口关闭守卫，不会提示未保存修改。窗口关闭按钮与 `Cmd+W` 会显示中文确认。
- 关闭确认对话框打开时按 Escape 也会关闭设置面板：两者都在 window 级监听 keydown，属于既有的模态协作限制。
- 关闭确认打开期间，App 层会忽略菜单动作与文件拖放，但原生菜单项本身不会置灰。

## 字体

- 随包内置八款 SIL OFL 1.1 字体：思源黑体（Noto Sans SC，默认 CJK 回退）、思源宋体（Noto Serif SC）、朱雀仿宋、霞鹜文楷、得意黑、马善政毛笔楷书、站酷小薇、站酷庆科黄油，以及 PDF base-14 字体；全部复用 CIDFontType2 + FontFile2 子集管线并完成再分发许可复核，出处与 SHA-256 见 `src-tauri/fonts/SOURCE.txt`，决策见 [ADR-0014](adr/0014-bundled-font-variety-and-original-font-restyle.md)。
- 本机已安装的字体（系统字体，以及 WPS Office 随版本提供的宋体、仿宋等）在运行时扫描后加入字体列表，分入“WPS 字体”与“本机字体”两组；字体文件不会被复制进仓库或安装包，每台机器看到的是它自己安装的字体。决策与许可理由见 [ADR-0015](adr/0015-installed-system-and-wps-fonts.md)。
- 八款内置字族与可选的本机字体都出现在“文本样式”的字体列表中；字号可输入 4–400 pt，也可从 WPS 风格的常用字号（8、9、10、10.5、11、12、14、16、18、20、22、24、26、28、32、36、42、48、56、64、72）中选择。
- 只有 Noto 两款有字重轴，粗体真正使用 700 字重；朱雀仿宋、霞鹜文楷、得意黑、马善政毛笔楷书、站酷小薇、站酷庆科黄油只有 Regular 一个实例，选粗体时保持常规轮廓。六款单实例内置字体与大多数本机字体没有斜体，选择斜体会返回“不支持字体”的错误。
- 编辑 PDF 原有文字时，若原字体是任意嵌入字体且不在可选列表内，面板默认保留原字体：只改字号或颜色会用原字体重新排版，仅替换字号与填充色；粗体、斜体、下划线与对齐需要先改选其他字体（该文本框随之转换为内置字体）。见 [ADR-0014](adr/0014-bundled-font-variety-and-original-font-restyle.md)。即使本机安装了同名字体，“原字体”仍是默认项，因为只有 PDF 内嵌的字体程序能保证与原文档逐字形一致。
- 原字体无法保留时（未嵌入的任意字体、不在列表内的 base-14 PostScript 名等）或原字体缺少要写的字时，回退顺序为：原字体嵌入程序 → 本机同一字族 → PDF base-14（仅 WinAnsi）→ 内置字族（仿宋类 → 朱雀仿宋，其他衬线 → 思源宋体，其余 → 思源黑体）。使用本机同名字体时不显示回退提示，因为文字外观没有可见变化。
- 字体扫描只接受带 `glyf` 轮廓的 TrueType/TrueType Collection 字体，并遵守 OS/2 `fsType` 嵌入权限：仅安装位、受限位或位图嵌入位打开的字体不会出现在列表。OpenType CFF 轮廓（如部分系统黑体）与没有直立字面的字体同样被跳过；macOS 上 PingFang 因 `fsType` 为 4 而被排除。
- 字体列表依赖本机安装情况：没有安装 WPS Office 的机器看不到 WPS 字体；同一文档在不同机器上可选的字体可能不同。首次扫描约需 0.6–0.75 秒（debug 构建），结果缓存在进程内。
- 朱雀仿宋是 v0.212 技术预览版，字表为 GB2312 级别：仿宋缺字时按朱雀仿宋 → 思源宋体 → 思源黑体回退。新增的五款字体原始文件合计约 47 MB（其中霞鹜文楷 25 MB），会明显增大安装包。
- ADR-0006 列出的 Inter、Noto Serif、Liberation Sans/Serif 尚未打包，见 [ADR-0011](adr/0011-initial-shipped-fonts.md)。文档原字体按字符优先复用；缺字形的字符先尝试本机同名字体，仍缺少时才回退到内置字体并提示。

## 命令边界与架构

- 边界使用领域命令（`apply_text_edit`、`insert_image`、`create_text_markup_annotation`、`save_document` 等），而不是规格示意中的通用 `begin_session/apply_edit/undo/redo` 信封。Tauri 命令边界仍然只有一个，`src/lib/backend.ts` 是前端唯一入口。
- 页面内容、注释与链接共用统一编辑历史，但页面操作、表单结构编辑等各有自己的恢复动作类型；这是实现选择，不是待修复缺陷。
- 以下重构属于已接受的债务，留待后续专项处理：拆分 `App.tsx` 与 `save.rs`；合并四处原子写实现；统一目标路径/权限守卫；替换按字段种类展开的 `match`；引入共享的矩形类型。

## 图层

- 图层面板列出文档级 Optional Content Group（`/OCProperties /D /OCGs`），而不是只列当前页的图层。PDF 的 OCG 本身就是文档级对象。
- 隐藏图层的文字仍会出现在文本提取与文本层中，因为 PDFium 的文本提取器忽略 OCG 可见性；若在提取阶段过滤，会与使用活动文档映射字符索引的文本编辑目标错位，导致编辑命中错误对象。

## 链接

- 源文档页面内容中的图片可以选择并添加链接，但只识别页面顶层的图片对象（`PdfPageObjectType::Image`）。嵌套在 Form XObject 内部的图片不可选。
- 已插入的会话图片（`page_images` 返回的对象）由图片编辑覆盖层管理，不出现在源图片链接目标中，避免同一区域出现两套可点击热区。

## 附件

- 打开附件前会再显示一次中文确认。这是超出票 36 所述“仅删除需确认”的有意安全增强，不是规格要求的回退。

## macOS 分发

- macOS 26.4 起会在检测到应用包含 Intel 组件时提示“对 Intel 芯片 App 的支持即将结束”。universal 构建为 Intel Mac 保留了 x86_64 切片，因此在 Apple Silicon 上也可能收到该通知；运行时仍是原生 arm64，不经过 Rosetta。这是 Apple 的弃用提示，不是 PDFX 的崩溃或安装错误。
- Apple Silicon 用户应使用 `npm run build:macos:arm64` 生成的 `PDFX_0.1.0_arm64.dmg`。脚本会把包内 PDFium 裁剪为 arm64、重新做 ad-hoc 签名，并拒绝任何残留的 x86_64 Mach-O 切片。Intel Mac 继续使用 universal 构建；macOS 27 是 Apple 最后一个支持 Intel Mac 的版本。
- Tauri 的 bundler 默认写入 `LSRequiresCarbon=true`。PDFX 通过 `src-tauri/Info.plist` 将其覆盖为 `false`，避免 Launch Services 把 Cocoa 应用标记为旧式 Carbon 应用；这与上面的 Intel 通知无关。
- 已经在通知中心出现的旧提示不会因替换应用而自动消失，需要手动清除。

## 验证状态

- 以下人工验收未在本环境执行：真实阅读器（Preview、Adobe Acrobat Reader、Chrome）中的打开/编辑/保存/链接点击矩阵；Windows 实机安装、文件关联与打印；较旧 macOS（含 macOS 12 与 Intel 硬件）实机启动；操作系统文件关联注册/取消的端到端流程；原生菜单与快捷键的人工验收；真实打印机输出与 macOS 原生打印面板的 `afterprint` 行为；真实 2000 页文档在桌面 WebView 中的内存曲线；真实磁盘写满时的写入行为（自动化使用注入错误与只读目录模拟）。
- macOS 26.4+ 的“Intel 芯片 App”通知是否在 arm64 构建上彻底消失，无法通过自动化读取通知中心来确认。已确认包内所有 Mach-O 文件均为 arm64、Launch Services 记录为 `native` / `arm64`、运行进程为 ARM64；通知中心里已经存在的旧提示需要手动清除。
- 自动化覆盖范围是命令边界、PDFium 适配层、lopdf 结构解析与 React 组件/原型交互，不等同于上述人工验收。
