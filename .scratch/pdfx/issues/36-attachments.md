Independently verified behavior:

- Model: attachments live in the catalog `/Names /EmbeddedFiles` name tree as `/Filespec` dictionaries (`/Type`, `/F`, `/UF`, optional `/Desc`) pointing at `/EmbeddedFile` streams (`/Subtype` MIME name, `/Params /Size`); nested `/Kids` trees are read correctly. The session keeps a baseline read through the same PDFium document the UI sees and derives remove/create sets at save, so untouched attachments are never rewritten. Existing attachments from the office corpus fixture survive adding and saving (`existing_corpus_attachment_survives_saving_an_added_attachment`); unrelated name trees (`/Dests`) are preserved (`unrelated_name_trees_survive_attachment_saves`); the name tree is rebuilt as one sorted, deduped leaf, so duplicate names cannot collide (`duplicate_attachment_names_get_a_stable_suffix`). A deleted attachment under a PDFDocEncoding name-tree key (`café.txt`, byte 0xE9, no `/UF`) is now actually removed (`deleting_a_pdfdocencoding_named_attachment_removes_it_from_the_saved_tree`); the audit found the old UTF-8 decoder produced U+FFFD so the removal name never matched, and `decode_pdf_text` now implements PDFDocEncoding (PDF 32000-1 Annex D.2).
- UI: `AttachmentPanel` lists 名称/大小/类型, adds through the native file picker, offers save-as through the native save dialog, asks for confirmation before opening (unsafe-attachment warning) and before deleting, and shows loading, empty, read-only and capability-restricted states plus Chinese messages for every attachment error code. Adding and deleting publish their history so the dirty marker and native menu update (`onHistory={save.acceptHistory}`). Panel tests cover each flow (`src/components/AttachmentPanel.test.tsx`, 15 tests), with App routing/history wiring in `src/App.test.tsx` and the list hook in `src/lib/useAttachments.test.tsx`. The panel is a new aside; annotation and form panels are untouched.
- Save/history: attachment edits ride inside ticket 10's single pipeline. `serialize_live_document` computes the attachment edit and `finalize_lopdf_revision` applies it in the same revision as the PDFium serialization; an attachment-only save appends exactly two cross-reference sections — one PDFium revision and one lopdf revision — and the saved file begins with the source bytes (`an_attachment_save_appends_one_pdfium_and_one_lopdf_revision`). Repeat saves are stable, the Source Document's bytes and mtime are unchanged (`repeated_saves_stay_stable_and_leave_the_source_untouched`), and an undone insertion never leaks into a save (`undo_and_redo_cover_adding_an_attachment`). Undo/redo restores the exact list, ids and order after both add and delete, with byte-identical attachment content after redo (`deleting_an_attachment_updates_the_saved_tree_and_undo_restores_it`). The unified history feeds the dirty/close guard from ticket 44.
- Flatten/export: flatten-export uses `serialize_live_document`, so an unsaved session-added attachment appears in the flattened copy and existing attachments are not dropped (`flattened_copy_keeps_attachments`: `a.txt`, session-added `flatten.bin`, `报告.pdf`, byte-identical). This was the audit's likely-defect area; a probe and the permanent test confirm the export does not bypass the attachment edit.
- Open security: an attachment is never opened automatically; `open_attachment` refuses without the two-step confirmation (`attachment_open_confirmation_required`) and extracts nothing before confirmation. Confirmed opens extract into the app cache staging directory under a sanitized base name — a hostile name cannot escape the directory (`staged.parent() == staging_root`) — then hand the path to the OS default handler through the injectable `open_attachment_with(..., launch)` seam; there is no shell interpolation, and the handler is invoked directly on the path. `opening_an_attachment_requires_confirmation_and_stages_safe_bytes` asserts the staged bytes are byte-identical and the unconfirmed path never launches. No network access is involved.
- Target protection: save-as writes atomically and refuses the Source Document and the current Output Document, including symlink and case-insensitive aliases through `target_path::same_file`; a refused save leaves the target bytes unchanged and the extracted output is byte-identical (`save_attachment_as_refuses_the_source_and_output_documents`, `save_attachment_as_extracts_exact_bytes_before_and_after_reopening`).
- Limits and errors: 100 MiB per attachment and a 120-character name cap are enforced with Chinese messages; long stems keep their extension and duplicate suffixes stay within the cap (`attachment_names_stay_within_the_character_cap`). Missing files (`file_not_found`), directories (`file_read_failed`) and oversized files (`attachment_too_large`) fail cleanly without touching the session or history (`attachment_file_errors_are_reported_before_touching_the_document`). Hostile names (`..\..\escape.txt`, control characters, `CON.txt`) are sanitized and stored intact in the tree (`hostile_attachment_names_cannot_escape_or_corrupt_the_saved_pdf`); the save dialog is offered only the base name of an existing attachment. Read-only documents refuse add and delete with `permission_denied` and leave the list untouched, while listing, opening and save-as still work (`read_only_documents_refuse_attachment_changes`); the UI disables add/delete and shows the Chinese read-only reason.
- Encrypted source: an attachment addition survives Save As to an unencrypted output, which still requires the explicit confirmation and leaves the encrypted source bytes untouched (`encrypted_source_save_as_requires_unencrypted_confirmation_and_keeps_attachments`).
- Packaging: no new dependencies (the pre-existing `open` crate, MIT, performs the OS handoff), no network/telemetry, no spec/ADR/packaging/capability changes, and the vendor tree is unchanged (15 files, 10 close types).

Limitations / manual items:

- Box 3 (real-reader matrix) is not checked: Preview, Adobe Acrobat Reader and Chrome were not available in this environment. Saved structure was asserted with an independent lopdf parse and a PDFium reopen; a manual export/open check in those readers remains.
- The OS-handler handoff is seam-tested only: `open_attachment_with` verifies the staged path passed to the launcher, but actually launching the platform handler (`open::that_detached`) was not exercised here.
- Opened attachments are extracted into the app cache and are not automatically deleted afterwards; they remain until the cache is cleaned or the OS removes them.
- The 100 MiB cap applies to added attachments; an existing attachment larger than the cap can still be listed and extracted.
- The `/EmbeddedFiles` rewrite flattens a nested `/Kids` structure written by another tool into a single sorted leaf. Every key, filespec, stream and unrelated name tree is preserved, but the original tree shape is not. No real-reader test exercises name-tree shape.
